# Проектирование агента/SaaS «Маркетолог» — следующая фаза

Capability Model зафиксирована и не пересматривается без новых внешних
фактов (Decision Monotonicity). Всё ниже — проектирование поверх неё, не
ревизия исследования.

---

## Responsibility Contract верхнего AI

Финальный сдвиг вопроса в исследовании: не «что делает профессия
маркетолог», а «за что отвечает верхний AI» — предмет сместился по ходу
работы, осознанно, не по ошибке. Название верхнего объекта («Маркетолог»,
Marketing Strategist, fractional CMO и т.п.) — решение продуктового
позиционирования на будущее, не архитектуры. Архитектуру определяет контракт
ниже.

**Отвечает:**

- за качество исследования аудитории (обоснованность вывода, не гарантию
  его окончательной верности)
- за обоснованность предложенного позиционирования и сообщения — как
  рекомендация с аргументацией, не как готовое решение
- за то, чтобы заметить конфликт нового решения с существующим брендом, не
  сгладить его молча
- за то, чтобы самому решить, когда вопрос слишком рискован для
  самостоятельного решения, и остановиться — это часть ответственности, не
  исключение из неё
- за корректность брифа, уходящего в Execution Engine

**Не отвечает:**

- за финальное решение публиковать что-либо (человек)
- за качество самого исполнения — текст/дизайн/доставка (Execution Engine)
- за результат на рынке (продажи, рост) — отвечает за качество решений, не
  гарантирует исход; рынок и действия людей вне его контроля
- за бюджет и распределение денег по каналам — не проектировали, открытый
  вопрос, совпадает с нерешённым GTM (Capability Model)
- за качество самого продукта/оффера бизнеса — Offer Design остался
  Underdetermined в Capability Model, поэтому и этот пункт открыт, не
  отвечает по умолчанию

Последняя граница («отвечает за качество решений, не гарантирует результат
на рынке») структурно совпадает с уже существующей границей роли AO в
CLAUDE.md («AO отвечает за то, чтобы экосистема была способна довести цель
до результата — не гарантирует сам результат бизнеса»). Замечено постфактум,
не подогнано заранее — тот же паттерн ответственности повторился на другом
уровне независимо.

## Черновая архитектура продукта (SaaS, независимо от Capability Map)

Публичные сущности, внутренние Engines, внутренние Skills — набросок,
организован по критериям продукта/масштабируемости/владения, не по
Capability Map (по прямому требованию Марии, чтобы не подгонять одну модель
под другую). Полный разбор — в переписке 2026-07-26, здесь фиксирую только
итоговое деление:

- **Strategy Engine** — Audience Research, Positioning, Messaging, Brand
  Strategy вместе. Низкая частота, требует суждения и человека в цикле —
  причина объединения инженерная (нагрузка), не капабилити-логика.
- **Execution Engine** — генерация контента (вероятно тонкая обвязка над
  внешними LLM/контент-API, не собственная разработка), оркестрация кампаний,
  доставка. Высокая частота, независимый скейлинг.
- **Insight Engine** — измерение, аналитика, эксперименты. Другой стек
  данных (event pipeline, не LLM-вызовы).
- **Governance** — согласования, аудит, версии, права. Сквозной слой, не
  капабилити маркетинга — то, что делает продукт продаваемым (доверие как
  фича), обслуживает Responsibility Contract выше технически.

Наблюдение (не результат отдельной проверки, зафиксировать честно):
Strategy Engine почти совпал по составу с ядром Capability Model, хотя
строился по независимым критериям — совпадение по разным причинам
(инженерным и профессиональным), не подгонка одной модели под другую.

**Обновление 2026-07-27:** этот набросок — грубое деление, не детальная
механика. Авторитетная детализация Strategy Engine (Responsibility-матрица,
Capability Selection, жизненный цикл Business Assets, Validate/Constraint) —
`../specializations/marketing_agent.md` v1.4. Не противоречит, но при
расхождении в деталях источник истины — marketing_agent.md, не этот черновик.

## idea-calibration.md — Шаги 0-6 (сделано самостоятельно, не по запросу)

**Шаг 0 — CS Trigger.** Impact: high (новый агент, системный артефакт). Uncertainty: была high, закрыта этой сессией (Capability Model + 21-кейс SaaS-исследование). Complexity: high (несколько открытых пунктов, межслойный Responsibility Contract). Хотя бы одна ось high → gate обязателен.

**Шаг 1 — Problem Definition.** Текущее состояние: у Мегаполиса нет верхнеуровневого маркетингового AI, отвечающего за стратегический слой (Audience Research/Positioning/Messaging/Brand) — пустой узел Capability Map, зафиксированный ещё 2026-07-24/25. Желаемое состояние: работающий Strategy Engine, реализующий Responsibility Contract. Кто испытывает: Мегаполис (Execution Priority №1, `projects/registry.md`), в перспективе — рынок агентств (SaaS-видение).

**Шаг 2 — World Research.** Выполнено этой сессией целиком: Направления 1-6 (профессия), 21-кейс SaaS-архитектур. Не повторяю.

**Шаг 3 — Три альтернативы.**

- **A (Minimal).** Bootstrap одного Strategy Engine для Мегаполиса — один системный промпт/tool-calling поверх 4 ядровых capability, без multi-agent, без SaaS-инфраструктуры. Time to working loop: дни.
- **B (Scale).** Сразу полная SaaS-архитектура (Strategy/Execution/Insight/Governance, multi-tenant) под агентства. Time to working loop: недели-месяцы.
- **C (Hybrid).** Bootstrap минимального Strategy Engine только для Мегаполиса сейчас, но границы (Responsibility Contract, разделение на Engine) проектируются так, чтобы не потребовалось переписывать архитектуру при переходе к SaaS позже.

**Шаг 4 — Trade-offs.**

| Вариант | Плюсы | Минусы | Риски |
| --- | --- | --- | --- |
| A | Быстро, дёшево, соответствует Working Loop First | Возможна переделка при масштабировании | Архитектура может не пережить рост |
| B | Сразу целится в конечную цель | Прямо нарушает `life_context.md` («Продукты для агентов — не успевают до cashflow-окна») и `user_maria.md` («Overengineering до данных») | Высокие — нарушает два уже принятых ограничения |
| C | Соответствует Working Loop First + не запирает будущее (согласуется с находкой №3 SaaS-исследования — архитектура обратима) | Требует дисциплины в границах сейчас | Умеренные |

Самый простой: A. Самый безопасный: C. Fastest to working loop: A. Сложнее всего поддерживать: B.

**Шаг 5 — Routing Decision.** Маршрут 5 (Новый агент) — Capability Map уже подтвердила пустой узел, ни один существующий агент Мегаполиса (landing_page_agent, Content Production, Distribution, CRM-Retention) не покрывает Audience Research/Positioning/Messaging/Brand Strategy. Внутри маршрута — **Вариант C**.

**Routing Falsification:**
- Почему НЕ нужен новый агент? Могли бы существующие агенты покрыть это? — Нет, узел пуст, зафиксировано независимо дважды (2026-07-24/25 и в этой сессии).
- Какие предположения под риском? Что Мегаполис — единственный реальный клиент прямо сейчас (SaaS — видение, не проверено вторым клиентом); что Advisory Mode (человек в цикле) не замедлит Марию на практике — не проверено.
- Что говорит против? `life_context.md`: cashflow — приоритет №1, срочность отмечена явно; ещё один агент — ещё один объект внимания в момент, когда фокус должен быть на финансах.
- Можно ли проверить дешевле? Да — прогнать ОДИН реальный маркетинговый вопрос Мегаполиса вручную по Responsibility Contract, не строя агента, прежде чем вкладываться в архитектуру.

**Шаг 6 — Decision Point.** Рекомендация: **Experiment**, не прямое Yes. 2-недельный scope: взять один реальный вопрос Мегаполиса (например, обновление Positioning Statement) и пройти его вручную/полу-автоматически по Responsibility Contract. Exit criteria: получили полезный, применимый артефакт (Audience Profile/Positioning Statement) → переходим к Bootstrap Strategy Engine (Вариант C). Не получили пользы или контракт не выдержал реальной задачи → возвращаемся к Capability Model, не строим агента.

Confidence: **Medium** — исследование сильное и трёхкратно перепроверенное, но ноль практической валидации на реальной задаче Мегаполиса.

## Что остаётся перед реальной постройкой агента

Не делаю сейчас, фиксирую как следующий шаг: Capability/Skill/Agent Design
по `idea-calibration.md` Шаги 3-7 (три альтернативы, trade-offs, routing
decision + falsification) и, поскольку это новый агент с системным
изменением ownership, — Architecture Review перед принятием
(`skills/architecture-review.md`, Independent Validation по CLAUDE.md).
Ничего из этого не выполнено этим документом — он фиксирует контракт и
черновую архитектуру, не запускает Bootstrap.

## Обновление — исследование архитектуры 21 успешного AI-native SaaS

См. `2026-07-26_saas-architecture-patterns-research.md` (полная таблица +
9 принципов). Ключевое для черновой архитектуры выше: разделение
Strategy/Execution/Insight Engine + Governance согласуется с находкой №1
(«пользовательская единица доверия одна, сложность внутри спрятана») и
№4 (проверка/эскалация появляется именно там, где дорога ошибка — ровно
Strategy Engine). Настоящий multi-agent (находка №2) — редкость даже у
успешных продуктов; решение НЕ строить множество внутренних именованных
агентов для ядра, а держать один Strategy-слой, согласуется с выбором
большинства успешных аналогов (не потому что скопировано, а потому что
паттерн подтвердился независимо).
