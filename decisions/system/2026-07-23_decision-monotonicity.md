# Decision Monotonicity

> История решения. Сами правила живут в `CLAUDE.md` (Операционные принципы).

---

## Контекст

Сессия обучающего разбора репозитория `mattpocock/skills` (Matt Pocock, автор
Total TypeScript). Отдельно разбирали его инженерный пайплайн
`grill-me → to-spec → to-tickets → implement` и заметили: каждый следующий
skill не имеет права переоткрывать решение предыдущего — только
конкретизировать или исполнять.

Параллельно в этой же сессии восемь раз подряд использовали похожую дисциплину
вручную при валидации Candidate Principles Brand Book Megapolis: вердикт →
решение Марии → LOCKED → следующий принцип не пересматривает предыдущий.

Возник вопрос: это два случайных совпадения или один и тот же архитектурный
инвариант?

---

## Проверка гипотезы

Абстрактная формулировка, предложенная для теста: решение проходит уровни
возрастающей определённости; уровень N+1 не пересматривает уровень N без
нового факта.

Проверено по пяти доменам:

- **Brand Book (эта же сессия)** — полное совпадение, причём уже было явно
  закреплено в самой AI_OS до этого разговора: лестница
  `Raw Observation → Hypothesis → Recurring Pattern` содержит правило «статус
  повышается только при независимом повторении, не потому что показалось
  важным» — то есть принцип уже действовал, просто без общего имени.
- **`decisions/` / ADR** — тоже уже существовало: `MAIN_ENGINEER/ENGINEERING_LOG/registry.md`
  прямо запрещает «менять исторические решения, редактировать прошлые выводы,
  чистить ошибки постфактум» (append-only). Подтверждено и практикой: сама
  ретроспектива `2026-07-21_retrieve-before-generate` не переписана, а
  дополнена разделом Addendum.
- **Пайплайн Мэтта Покока** — совпадение, плюс независимое подтверждение в
  другом месте того же репозитория: skill `resolving-merge-conflicts`
  содержит явное «never `--abort`» — тот же этос «только вперёд».
- **Reasoning Pipeline AI_OS** — только частичное совпадение. Семь шагов
  действительно сужают пространство решений (форма та же), но explicit-запрета
  «поздний шаг не пересматривает ранний без нового факта» там нет. Не
  подтверждение и не опровержение — домен, где паттерн просматривается по
  форме, но не закреплён как правило. Осознанно не редактировался — риск
  усложнения без evidence, что это нужно именно там.

По лестнице обобщения самой AI_OS (Raw Observation → Hypothesis →
Recurring Pattern, порог ≥2–3 независимых повторения) гипотеза перешла в
статус Recurring Pattern: три независимых уже существующих места плюс внешнее
подтверждение, без единого нового факта, придуманного специально под неё.

## Обсуждение названия

Первый вариант — «Progressive Commitment» — отклонён: описывает управленческий
процесс, а не эпистемическое свойство (как система работает со знанием).

Принято: **Decision Monotonicity**. «Монотонность» здесь — инженерный термин
(как в semver или monotonic clock): новая информация может уточнить состояние,
но не должна произвольно разрушать уже подтверждённое без новых оснований.

Оговорка: в формальной математической логике «монотонность» иногда означает
более узкое свойство (выводы вообще никогда не отзываются, только копятся) —
то, что описано здесь, ближе к defeasible reasoning с барьером доказательства.
Название не меняли из-за этого — инженерное словоупотребление (semver и т.п.)
устоявшееся и точно передаёт суть, — но оговорка зафиксирована, чтобы не
пришлось объяснять заново при столкновении с формальным математическим
контекстом.

Формулировка усилена относительно первого черновика: изначально «без нового
факта», добавлено «или выявленной ошибки в исходных предпосылках» — потому что
пересмотр Principle 7 (Radical Confidentiality) в Brand Book произошёл не
из-за нового факта, а из-за обнаружения, что существующее доказательство
(property-analyst PROJECT_DNA) было изначально неверно процитировано. Это тоже
легитимное основание для возврата, и первая формулировка его не покрывала.

## Что решено НЕ делать

- **Не переписывать Reasoning Pipeline.** Совпадение там только по форме, не
  по правилу — редактирование ввело бы сложность без evidence, что она нужна
  именно в этом месте (см. проверку по доменам выше).
- **Не создавать новый skill или отдельный документ.** По Extend before
  Create — принцип добавлен одной записью в уже существующий раздел
  «Операционные принципы», плюс одна перекрёстная ссылка из уже существующей
  лестницы наблюдений. Никакой новой инфраструктуры.

## Addendum — Disambiguate before Execute + SPEC-условие (тот же день)

После фиксации Decision Monotonicity разбирали пайплайн Мэтта Покока
`grill-me → to-spec → to-tickets → implement` и обсуждали, стоит ли перенести
его в AI_OS целиком как обязательный режим работы («Grill / Spec / Tasks /
Execute»).

**Что не стали делать.** Не переносили пайплайн один в один и не закрепляли
сегодня ни строчки про Grill, Tasks, Skills или Routing — форма реализации
(встроенный lifecycle, Claude Skills, orchestrator) ещё не решена, закреплять
её раньше времени означало бы Method Change без завершённого World Research.
Кроме того, обязательный `grill-me`-по-умолчанию противоречил бы уже принятому
решению «уточняющие вопросы — только если концепция принципиально неясна»
(`context/user_maria.md`) — потребовалось бы сознательно его пересматривать,
а не тихо перекрывать.

**Что сделали вместо этого — два узких, уже готовых улучшения:**

1. **Disambiguate before Execute** (новый принцип) — не «задавай вопросы
   пользователю», а внутренняя дисциплина агента: снимать критическую
   неоднозначность самым дешёвым способом, вопрос — последний, а не первый
   инструмент. Проверено на непротиворечивость с «не переспрашивай без нужды».
2. **Дополнение к Decision Monotonicity** — практическое условие для
   многосессионных/архитектурных задач: SPEC фиксируется до изменений, не
   после. Это не новый принцип, а операционное следствие уже принятого —
   без зафиксированного SPEC монотонность нечем защищать через границу сессии.

**Что осознанно отложено.** Полноценный «Execution Lifecycle AI_OS»
(Grill → Spec → Tasks → Execute как реальный вызываемый режим, не только
принцип в CLAUDE.md) — отдельная архитектурная задача следующей сессии,
которая по только что принятому правилу сама обязана начаться с SPEC, а не
с кода.
