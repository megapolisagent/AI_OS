# Гипотеза: Concept Before Architecture

> Это не принцип AI_OS. Это кандидат в принцип, зафиксированный для проверки повторяемости.
> Pattern Capture (CLAUDE.md) требует «устойчивого» паттерна перед превращением в постоянный артефакт — на момент записи есть только один случай (n=1). Повышать до принципа CLAUDE.md преждевременно.

---

## Формулировка гипотезы

> Если проект создаёт новую систему поведения (human или AI) — не только рабочий артефакт — сначала определить желаемую трансформацию, затем проектировать архитектуру (Student Model / Curriculum / Decision Rules / routing / что угодно техническое).

Явно **не** ограничено задачами про людей — включает CRM, агентов, AI_OS-изменения routing, что угодно, где успех измеряется изменением поведения, а не только существованием артефакта. Явно исключает чистую инфраструктуру (Knowledge Base, хранение) — там нет «трансформации», уже покрыто Single Source of Truth и Test Before Add.

---

## Откуда взялась

Проект English Tutor (см. `decisions/projects/english_tutor_architecture_handoff.md`, сессия 2026-07-17/18). Архитектура строилась последовательно, отвечая на явные требования Марии (голос, самостоятельность, память, режимы), и была технически сильной — но оставалась в рамке «репетитор/curriculum» несколько десятков ходов подряд, пока внешний независимый ревьюер (не Claude) не задал другой вопрос: не «что ребёнок должен знать», а «что должно измениться в ребёнке через два года». Это привело к полной пересборке центра архитектуры (Tutor → Companion → Relationship Engine → World Engine → Mission-first), при том что все технические механизмы (Student Model, spaced repetition, decision rules) остались годными — сменился только организующий центр.

Ключевое наблюдение исполнителя (Claude) в момент разбора: research и architecture шли подряд без промежуточного шага, на котором явно формулируется желаемая трансформация. Существующий цикл был `Research → Architecture → Review`; предлагаемый — `Research → Concept → Architecture → Review`.

---

## Что явно РЕШЕНО не делать (и почему)

**Не добавлять «изменение критерия успеха» как отдельный триггер в Independent Validation.** Если Concept Before Architecture соблюдается как дисциплина, смена цели на нетривиальном проекте и так пересобирает Concept → Architecture заново, что естественно попадает под уже существующий триггер «сложный архитектурный анализ». Отдельный триггер избыточен при условии, что первичный механизм (пересборка от Concept) работает.

**Не размещать этот файл в личной памяти исполнителя.** AI_OS explicit executor-agnostic (`routing/registry.md`: capability отделена от исполнителя — Claude/Codex/Gemini). Знание, привязанное к памяти конкретного экземпляра модели, невидимо для другого исполнителя, который в будущем возьмёт Architecture Review или Execution по другому проекту. Гипотеза AI_OS должна жить в файловой системе, не в памяти конкретного агента.

## Условие превращения в принцип CLAUDE.md

Если этот же паттерн — архитектура построена и технически состоятельна, но не решает истинную задачу, потому что desired-transformation не была сформулирована explicitly до начала проектирования — повторится ещё в 1-2 независимых, содержательно не связанных с English Tutor проектах, тогда:

1. Добавить `Concept Before Architecture` как принцип в CLAUDE.md (рядом с Working Loop First — сопоставимый по типу: методологический/sequencing принцип, не только ownership/routing)
2. Этот файл — архивировать со статусом «подтверждена, повышена до принципа [дата]»

Если паттерн не повторится в разумный срок (условно — несколько независимых проектов) — этот файл остаётся архивной гипотезой, не становится принципом. Это тоже валидный исход, не провал.
