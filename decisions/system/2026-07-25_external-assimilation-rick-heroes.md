## Источник

6 файлов (не 9, как изначально заявлено) из workspace `idkras/heroes-rickai-workspace`,
автор Илья Красинский, © Magic Rick Inc. — копирайт прямо запрещает
использование/копирование/адаптацию без письменного согласия автора. Ниже —
только архитектурные идеи (уровень концепции, не текста/формул), не
скопированный или адаптированный материал.

## Главный вывод

Rick-система решает другую задачу, чем `capability-creation-methodology.md`:
контроль качества и прослеживаемости уже понятных инженерных тикетов внутри
известного workspace — не исследование незнакомой профессиональной области.
Проверено практически: прогон «Marketing Capability» через их методологию
останавливается на Шаге 0, потому что она предполагает уже понятный контекст.
**Не замена AI_OS Discovery/Design, кандидат только на Execution-стадию**
(после Bootstrap Sequence — граница уже существовала в `architecture-review.md`,
не изобретена в этом цикле).

## Итоговый список кандидатов на будущее (не решено, не построено)

✅ **Количественный Validation** (числовой скоринг вместо Low/Medium/High) —
реальный кандидат, если найдётся конкретная задача, где это действительно
нужно. Не спроектирован.

✅ **Более гранулярная Outcome-лестница** (не бинарно output/outcome, а
несколько уровней с повторяемым тестом остановки) — усиливает Outcome
Accountability. Не спроектирован.

⭐ **Обязательная трассируемость происхождения правила через инцидент**
(Problem → Incident → Decision → Rule) — по итогам обсуждения признано
сильнее двух предыдущих. Подтверждено фактом этой же сессии: self-audit
утром нашёл потерю Stage Awareness/Decision Freeze/Priority Hierarchy при
миграции MAIN_ENGINEER → AI_OS, не замеченную никем, пока не искали
специально. `decisions/` уже существует, но связь с конкретным правилом в
CLAUDE.md — по памяти читателя, не структурная. Это и есть отличие.

❌ **Hard Reuse-режим** — рассмотрен и отклонён. Не новый механизм, а вопрос
строгости исполнения уже существующих (Extend before Create, Legacy-first
Alarm, Routing Falsification). Условие пересмотра: 2-3 независимых случая,
где существующие механизмы реально не остановили лишнюю сущность — не
раньше.

## Явно не решено сейчас

Ни один из кандидатов не спроектирован и не встроен. Решение о том, стоит
ли вообще их строить, требует Independent Validation при реальной попытке
(Capability Design/Evolution), не выносится этим циклом сравнения.

## Обновление 2026-07-28 — более полные артефакты того же источника

Прочитан более полный пакет того же workspace (не новый источник): 2 субагента
(`outcome-designer.md`, `jtbd-scenarium-tracker.md`) + 3 SKILL.md + тесты,
пакет «Нейросаммит-18» от того же автора. Копирайт тот же — анализ на уровне
архитектуры, не копирование формулировок.

**Независимая конвергенция (усиливает, не новый вывод).** Их hard-fail R1
(`outcome-designer.md`) — «downstream JTBD другой роли выдан за outcome этой
задачи» — структурно совпадает с Problem Fidelity, добавленным в
`skills/architecture-review.md` в этом же цикле 2026-07-28 (см.
`2026-07-28_independent-validation-scope-expansion.md`). Четвёртая
независимая система (после Rick/Heroes-концепции здесь же, Blueprint Agent
System, и собственного наблюдения AI_OS с дашбордом), называющая один и тот
же failure mode — задним числом подтверждает, что добавленный пункт целится
в реальный, не выдуманный класс ошибки.

Их «Demo-readiness gate» (A1-A7: доступ → запуск → тест → демо) — рабочий,
проработанный пример именно той Readiness-ступени, которая с 2026-07-24
висит нерешённым Open Question в `AI_OS_LIFECYCLE.md` (кейс Landing Page
Agent). Конкретные 7 проверок специфичны их стеку (npm/Docker/submodule) —
не переносятся дословно, но сам факт независимой конвергенции на этой же
недостающей ступени — дополнительный вес в пользу того, что вопрос реальный.

Формула gap/effort/goodness (geometric mean, протестированный код) —
рабочий пример уже отмеченного выше кандидата «Количественный Validation» —
остаётся отложенным, конкретной задачи AI_OS для него по-прежнему нет,
теперь есть референсная модель на случай появления.

JTBD Scenarium/Ticket/Skill Writer — качественная методология, но для
продукта/тикетов конкретной dev-команды (Beads, protected paths) — по
Principle 0 материал уровня проекта, не AI_OS.

So-What Outcome Ladder и Expected Output Announce-гейт — рабочие механики
для команды из многих параллельных агентов на живом проде; для AI_OS без
такого объёма и без зафиксированного инцидента, который бы их обосновал —
осознанно не берём (Minimal Sufficiency).
