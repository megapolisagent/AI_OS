# Ретроспектива: Retrieve before Generate, Extend before Create

> История решения. Не место для рабочих инструкций — сами правила живут в
> `CLAUDE.md` (Операционные принципы), рабочий метод — в `skills/taste-capture.md`.

---

## Контекст

Сессия 2026-07-21. Разработка Brand Book для Megapolis (проект вне AI_OS, но
паттерны, обнаруженные в процессе, — архитектурные, применимы ко всей экосистеме).

---

## Паттерн 1 (углублённая формулировка) — Assume nothing. Retrieve first.

**Симптом:** за сессию трижды независимо предполагалось отсутствие артефакта вместо
проверки его существования — (1) готовность исследовать конкурентов рынка Москвы с
нуля, (2) предложение эстетических архетипов «из головы» до чтения TOV/Foundation
Strategy, (3) готовность строить новые сущности до проверки того, что уже покрыто
существующей архитектурой.

**Почему:** это не просто «гадание по памяти» — точнее: предположение об
отсутствии не было проверенным действием ни разу из трёх случаев. Проверка
файловой системы воспринималась как разовый шаг в начале сессии, а не как рефлекс
на каждую новую подтему.

**Влияние:** несколько раундов пересборки того, что уже существовало в
`БАЗА ЗНАНИЙ` — TOV v3.1, Миссия и ценности, Foundation Strategy, конкурентный
анализ с палитрой.

**Правило:** Retrieve before Generate — Assume nothing.

---

## Паттерн Г — создание новой сущности вместо расширения существующей

**Симптом:** первое движение на новый вопрос — предложить новый документ, новый
агент, новый этап или новый framework, а не расширить то, что уже есть.

**Почему:** естественная склонность структурировать задачу через новую сущность,
даже когда существующая архитектура уже покрывает большую часть потребности.

**Влияние:** рост сложности системы, лишняя инфраструктура — если бы паттерн не
был пойман, сессия закончилась бы отдельным «Brand Framework», отдельной «Creative
Platform» и отдельным «большим процессом» вместо расширения уже работающих
артефактов.

**Подтверждающие случаи из той же сессии (что сделали вместо):**
- вместо нового исследования конкурентов → Gap Analysis (закрыт только реальный
  пробел — международный бенчмарк, Москва уже была исследована)
- вместо нового Brand Framework → Evidence Board (расширение уже начатого
  документа, не новый тип артефакта)
- вместо большой Creative Platform (200 референсов, luxury fashion, digital-агентства)
  → Taste Capture (тот же документ, накопительный, без отдельной инфраструктуры)

**Правило:** Extend before Create — новая сущность создаётся только при появлении
новой ответственности, не новой информации. Перед созданием — явный вопрос: какой
существующий артефакт можно расширить?

---

## Что решено НЕ добавлять отдельным принципом

**Evidence before Conclusions** — рассматривалось как отдельное правило, но при
проверке оказалось покрыто уже существующими `Method Change Requires World
Research` и эпистемическими маркерами (ЗНАЕМ/ПРЕДПОЛАГАЕМ/НЕ ЗНАЕМ). Добавление
отдельным пунктом нарушило бы Principle 1 (Single Source of Truth) — дублирование
вместо усиления. Вместо этого добавлена more specific лестница для субъективных
наблюдений (см. ниже) — она не покрыта существующими маркерами, потому что описывает
не статус утверждения, а путь его повышения во времени.

- **Extend before Create** (Операционные принципы)

Отдельного файла `CORE.md` не создано — сама постановка вопроса («создать
отдельный CORE») была проверена на соответствие только что принятому Extend before
Create: в AI_OS `CLAUDE.md` уже структурно является core-документом (Principles +
Reasoning Pipeline). Создание параллельного файла было бы нарушением правила,
которое мы в этот же момент фиксируем.

## Для будущего исполнителя

Если ловишь себя на «нужно исследовать/создать X» — сначала одна проверка:
существует ли уже источник или сущность, которую можно расширить. Это не
бюрократия — это дешевле, чем цикл «предложил → отвергли → нашли готовое».

## Addendum — Adopt before Build (тот же день, тот же паттерн шире)

После первой версии ретроспективы обнаружился ещё один слой того же паттерна:
при сборке кастомных инструментов внутри сессии (Taste Swipe) не была проверена
внешняя экосистема Claude Code/Anthropic/GitHub/community на предмет готового
примитива — хотя в Reasoning Pipeline уже существовал пункт 4 (Implementation
Selection), формально это покрывающий.

**Диагноз:** пункт 4 существовал, но на практике читался как «проверить то, что
уже замаплено в `routing/registry.md`», а не «проверить открытую экосистему, о
существовании чего я не знаю». Формально принцип был, фактически не срабатывал.

**Решение (скорректировано):** первая версия решения ошибочно поместила проверку
внутрь Implementation Selection (шаг 4/теперь 5) — но этот шаг отвечает за выбор
реализации уже принятого архитектурного решения, не за само решение. Проверка
экосистемы должна происходить раньше — на развилке «проектировать новое или нет»,
до Implementation Selection.

Финальное размещение: новый условный шаг Reasoning Pipeline —
**External Capability Check** (между Required Capability и Implementation
Selection), срабатывает только когда Required Capability предполагает новую
capability/workflow/skill/агента/архитектурный паттерн — не для рутинной задачи
внутри уже выбранной архитектуры. Не новая запись в Capability Registry (дублировала
бы Opportunity Discovery — та реактивна, срабатывает когда находку приносит
пользователь; здесь нужно проактивное срабатывание). Короткий принцип **Adopt
before Build** остаётся в Операционных принципах как декларативная память,
механика — в Reasoning Pipeline.

**Порядок теперь явно трёхшаговый:** своя файловая система (Retrieve before
Generate) → платформа/экосистема, условно (Adopt before Build / External
Capability Check) → только затем собственное решение.

**Уточнение триггера (тот же день):** первая формулировка гейта перечисляла типы
сущностей (capability/workflow/skill/агент/паттерн) — хрупко к появлению новых
типов сущностей и не покрывало случаи вроде «сделаем визуальную доску», формально
не подпадающие ни под один пункт списка. Предложенная альтернатива «любое решение,
которое потенциально может быть уже решено существующим инструментом» отклонена —
верна почти для любой задачи, сделала бы гейт триггерящимся почти всегда
(перетриггерение вместо недотриггерения). Принятая формулировка — тест по типу
решения, не по типу сущности: «изобретаем ли мы новый способ делать что-то,
которого в системе ещё нет» — перечисление типов сущностей оставлено как примеры,
не как исчерпывающий список.

**Уточнение №3 (тот же день) — порядок поиска внутри Adopt before Build.**
Гейт срабатывал, но без явного порядка поиска систематически скатывался к «что
нового у платформы» (MCP/SDK/GitHub-репозитории) вместо «кто уже решает эту
бизнес-задачу» (зрелые workflow, готовые агенты под конкретную предметную
задачу). Два независимых прогона исследования подтвердили это: первый исследовал
Claude Code как платформу, второй — снова скатился к инструментам (Figma MCP,
Knowledge Graph MCP, Tavily/Firecrawl) вместо готовых доменных решений (workflow
для consumer insight synthesis, агент для positioning research, skill для
competitor teardown).

Добавлен явный порядок поиска в Adopt before Build: домен-workflow → готовые
агенты → готовые skills → MCP → SDK/платформа. Без явного порядка принцип
формально существует, но систематически не достигает цели.
